NATS edge: cloud hub + site leaf nodes

Sites subscribe to the cloud over one outbound TLS connection. Reliable delivery in both directions, and a separate certificate and permissions for every leaf.

Architecture

Edge apps talk only to the NATS server on their own site LAN. The leaf node at each site dials out to the hub, so the site needs no inbound port and works behind NAT. Each side runs its own JetStream domain (cloud, site1, …), so the cloud can reach a site's streams as $JS.site1.API and a site can reach the cloud's as $JS.cloud.API, both over the same leaf connection.

Where each message waits during an outage

TrafficWaits onMechanism
Telemetry, health, command results (site → cloud)Site disk: SITE1_UPLINKThe edge app's JetStream publish is acked by the local server, so it succeeds with the WAN down. FLEET_UPLINK sources each site stream and resumes from its last sequence when the link returns. Order is kept, and Nats-Msg-Id deduplicates.
Commands (cloud → site)Cloud disk: FLEET_COMMANDSThe site pulls its own durable consumer siteN-commands through the leaf. Explicit ack; a work-queue stream deletes on ack.
Stale commandsDeleted in the cloudPer-message Nats-TTL (stream has allow_msg_ttl), so a stale command is never shipped. Keep the expiresAt check at the edge as well.
Latest health per robotFLEET_UPLINKA consumer with deliver_policy: last_per_subject on sites.*.health.>

Sizing: SITE1_UPLINK uses discard: new. When the site disk fills during a very long outage, publishes are refused (the app sees an error) rather than old unsent data being silently dropped. Size max_bytes from uplink rate × the longest outage you must survive.

Per-leaf security

Identity: one client certificate per site

The hub's leaf listener uses verify_and_map: true. Each site presents its own certificate signed by the fleet CA, and the certificate subject CN=leaf-siteN,O=fleet is the hub user. There is no shared secret and no password in a URL. Revoking one site touches no other site. A valid CA-signed certificate with an unknown subject is rejected.

Authorization: enforced on the hub, per leaf

Direction (hub's view)site1 may
publish (site → cloud)pull, read info on and ack only FLEET_COMMANDS.site1-commands; deliver uplink only on fleet.deliver.site1.>; $JSC.R.> for sourcing replies
denysites.*.command.*.req: a site can never inject commands, even for its own robots
subscribe (cloud → site)$JS.site1.API.> (the hub sourcing its stream), $JS.FC.>, _INBOX.>

The site LAN has its own limits: edge-app may publish only sites.site1.> (except command requests) and use its own consumer. site-ops exists for provisioning only. Even site-ops, with full rights on its own leaf, is refused by the hub when it asks for another site's consumer.

Configuration

config/cloud-hub.conf
# =============================================================================
# CLOUD HUB
#
# Owns the durable command queue (FLEET_COMMANDS) and the fleet-wide uplink
# (FLEET_UPLINK, sourced from every site's local stream).
# Sites dial in on 7422. The hub never connects to a site.
# =============================================================================
server_name: cloud-hub-1

# Same black-hole detection on the hub side, so the leaf DISCONNECT event in
# $SYS.ACCOUNT.FLEET.DISCONNECT (your site-offline signal) fires in ~1 min.
ping_interval: "20s"
ping_max: 2
listen: 0.0.0.0:4222            # cloud apps

jetstream {
  domain: cloud                 # sites reach this JetStream as $JS.cloud.API
  store_dir: "./data/cloud"
  max_file_store: 50GB
}

# --- client TLS (cloud apps) -------------------------------------------------
tls {
  cert_file: "./certs/cloud.crt"
  key_file:  "./certs/cloud.key"
  ca_file:   "./certs/ca.crt"
}

# --- leaf node listener: every site dials OUT to here ------------------------
leafnodes {
  listen: 0.0.0.0:7422
  # The hub ALWAYS tells connecting leaves its own leaf URL, and leaves add it
  # to their reconnect list. Left unset, that is the pod/VM's private IP, and
  # leaves will reconnect around your load balancer. Set it to the public name.
  # (no_advertise does NOT cover this: in v2.12.1 it only affects gossip to
  # cluster routes -- server/route.go, server/leafnode.go.)
  advertise: "cloud-hub:7422"
  tls {
    cert_file: "./certs/cloud.crt"
    key_file:  "./certs/cloud.key"
    ca_file:   "./certs/ca.crt"
    # Per-leaf identity: each site presents its OWN client cert, signed by
    # the fleet CA. The cert subject IS the username. No shared secret, no
    # password in a URL, and revoking one site never touches another.
    verify_and_map: true
    timeout: 5
  }
}

accounts {
  FLEET {
    jetstream: enabled
    users: [
      # cloud-app: issues commands, reads the whole fleet uplink.
      { user: cloud-app, password: $CLOUD_APP_PASS }

      # One identity per site = the subject of that site's client cert.
      # Permissions are from the HUB's point of view:
      #   publish   = what the site may send up into the cloud
      #   subscribe = what the cloud may send down to the site
      { user: "CN=leaf-site1,O=fleet", permissions: {
          publish: {
            allow: [
              # downlink: pull + ack its OWN durable command consumer only
              "$JS.cloud.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.site1-commands"
              "$JS.cloud.API.CONSUMER.INFO.FLEET_COMMANDS.site1-commands"
              "$JS.ACK.FLEET_COMMANDS.site1-commands.>"
              # uplink: deliver this site's stream into FLEET_UPLINK,
              # on a per-site prefix so site1 cannot write into another site's copy
              "fleet.deliver.site1.>"
              "$JSC.R.>"
            ]
            # a site may never inject commands, even for its own robots
            deny: [ "sites.*.command.*.req" ]
          }
          subscribe: {
            allow: [
              "$JS.site1.API.>"   # hub -> this site's JetStream API (sourcing)
              "$JS.FC.>"          # flow-control replies for the uplink copy
              "_INBOX.>"          # replies to the edge app's pull requests
            ]
          }
      }}

      { user: "CN=leaf-site2,O=fleet", permissions: {
          publish: {
            allow: [
              # downlink: pull + ack its OWN durable command consumer only
              "$JS.cloud.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.site2-commands"
              "$JS.cloud.API.CONSUMER.INFO.FLEET_COMMANDS.site2-commands"
              "$JS.ACK.FLEET_COMMANDS.site2-commands.>"
              # uplink: deliver this site's stream into FLEET_UPLINK,
              # on a per-site prefix so site2 cannot write into another site's copy
              "fleet.deliver.site2.>"
              "$JSC.R.>"
            ]
            # a site may never inject commands, even for its own robots
            deny: [ "sites.*.command.*.req" ]
          }
          subscribe: {
            allow: [
              "$JS.site2.API.>"   # hub -> this site's JetStream API (sourcing)
              "$JS.FC.>"          # flow-control replies for the uplink copy
              "_INBOX.>"          # replies to the edge app's pull requests
            ]
          }
      }}
    ]
  }
  SYS { users: [ { user: sys, password: $SYS_PASS } ] }
}
system_account: SYS
config/site1-leaf.conf
# =============================================================================
# SITE LEAF  --  site1
#
# Edge apps talk ONLY to this server, on the site LAN.
#  - Uplink (telemetry, health, command results): published into the local
#    stream SITE1_UPLINK. The publish ack comes from THIS server's disk, so it
#    succeeds even when the WAN is down. The cloud copies the stream when the
#    link is back.
#  - Downlink (commands): the edge app pulls its durable consumer on the CLOUD
#    stream through this leaf ($JS.cloud.API...). While the link is down,
#    commands wait in the cloud. Nats-TTL removes them once they are stale.
# =============================================================================
server_name: site1-leaf

# Detect a black-holed WAN (socket open, nothing flowing) in about a minute.
# Defaults are 2m x 2 outstanding (server/const.go), i.e. minutes of a dead
# link that still looks up. Measured with 20s/2: link dropped after 61s.
ping_interval: "20s"
ping_max: 2
listen: 0.0.0.0:4222             # site LAN only

jetstream {
  domain: site1                  # the cloud reaches this as $JS.site1.API
  store_dir: "./data/site1"
  # Size = uplink rate x worst outage you must survive, plus headroom.
  max_file_store: 20GB
  # Every write reaches the OS immediately, so a nats-server crash loses
  # nothing (measured: kill -9 mid-outage, 0 lost). fsync, though, runs only
  # every 2m by default (server/filestore.go defaultSyncInterval), so a POWER
  # cut can lose up to 2m of already-acked uplink. Sites lose power; this
  # closes that window. Measure the cost on the real site disk.
  sync_interval: always
}

accounts {
  FLEET {
    jetstream: enabled
    users: [
      { user: edge-app, password: $EDGE_APP_PASS, permissions: {
          publish:   { allow: [ "sites.site1.>", "$JS.API.STREAM.INFO.SITE1_UPLINK",
                                "$JS.cloud.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.site1-commands",
                                "$JS.cloud.API.CONSUMER.INFO.FLEET_COMMANDS.site1-commands",
                                "$JS.ACK.FLEET_COMMANDS.site1-commands.>" ],
                       deny:  [ "sites.site1.command.*.req" ] }
          subscribe: { allow: [ "_INBOX.>" ] }
      }}
      # provisioning only (creates SITE1_UPLINK); not used by apps
      { user: site-ops, password: $SITE_OPS_PASS }
    ]
  }
  SYS { users: [ { user: sys, password: $SYS_PASS } ] }
}
system_account: SYS

leafnodes {
  # Dial OUT. Works behind NAT. The site needs no inbound port.
  remotes: [
    {
      urls: [ "tls://cloud-hub:7422" ]
      account: FLEET
      tls {
        ca_file:   "./certs/ca.crt"
        # this site's identity; private key never leaves the site
        cert_file: "./certs/leaf-site1.crt"
        key_file:  "./certs/leaf-site1.key"
      }
    }
  ]
  # Actual delay is reconnect + random jitter up to reconnect
  # (server/leafnode.go), so 5s spreads a regional reconnect over 5-10s.
  reconnect: "5s"
}

gen-certs.sh
#!/bin/bash
# Fleet CA, hub server cert, and ONE client cert per site (per-leaf identity).
# usage: ./gen-certs.sh cloud-hub.example.com site1 site2 ...
set -euo pipefail
HUB=$1; shift; mkdir -p certs; cd certs
[ -f ca.key ] || openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 3650 -subj "/CN=fleet-ca"
openssl req -newkey rsa:2048 -nodes -keyout cloud.key -out cloud.csr -subj "/CN=$HUB"
printf "subjectAltName=DNS:%s\nextendedKeyUsage=serverAuth" "$HUB" > s.ext
openssl x509 -req -in cloud.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out cloud.crt -days 825 -extfile s.ext
for s in "$@"; do
  openssl req -newkey rsa:2048 -nodes -keyout leaf-$s.key -out leaf-$s.csr -subj "/CN=leaf-$s/O=fleet"
  printf "extendedKeyUsage=clientAuth" > c.ext
  openssl x509 -req -in leaf-$s.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out leaf-$s.crt -days 825 -extfile c.ext
  echo "hub user for $s: \"CN=leaf-$s,O=fleet\"   (form verified against nats-server 2.12.1)"
done
rm -f *.csr *.ext

Adding a site

./gen-certs.sh cloud-hub.example.com site3           # site3 key stays on site3
# hub: add user "CN=leaf-site3,O=fleet" (copy the site1 block, s/site1/site3/), reload
# site: copy site1-leaf.conf -> site3-leaf.conf, s/site1/site3/
nats --server site3 stream add --config SITE3_UPLINK.json
nats --server cloud consumer add FLEET_COMMANDS --config site3-commands.consumer.json
nats --server cloud stream edit FLEET_UPLINK          # add the SITE3_UPLINK source

Verification

Run on nats-server v2.12.1 and nats.go v1.46.1: one hub, two leaves, with site1's WAN routed through a TCP proxy that the test kills and restores. The harness and scenario are in test/.

What the test caught

1. Sourcing over a locked-down leaf. The first permissions draft blocked FLEET_UPLINK: the cloud received 0 messages and logged no error. The source consumer delivers on $JS.S.<rand> and gets its create reply on $JSC.R.<rand> (server/stream.go syncSubject("$JS.S"), server/jetstream_cluster.go infoReplySubject()). Setting external.deliver to a per-site prefix (fleet.deliver.siteN) moves the data onto a subject that can be scoped per leaf.

2. Leaves reconnecting around the load balancer. After the simulated WAN cut, site1 reconnected straight to the hub's private IP. A connecting leaf always receives the hub's own leaf URL (server/leafnode.go: s.leafURLsMap[s.leafNodeInfo.IP]++), and no_advertise only affects gossip to cluster routes (server/route.go). The fix is leafnodes.advertise set to the public name.

Open items

  • $JSC.R.> (publish) and $JS.FC.> / _INBOX.> (subscribe) are not per-site. They are random reply subjects, so the risk is low, but a site could in principle reach another site's reply subject. Separate accounts per site, with exports and imports, close this at the cost of more config.
  • Tested with a single hub node. Production needs a 3-node hub cluster (the JSON already sets num_replicas: 3) and a load balancer named in advertise.
  • Delivery is at-least-once: dedupe on commandId at the edge, and use Nats-Msg-Id on every uplink publish.
  • Certificate rotation and revocation (OCSP or a CRL on the leaf listener) are not covered yet.
