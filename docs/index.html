NATS edge: cloud hub + site leaf nodes

Sites subscribe to the cloud over one outbound TLS connection. Reliable delivery in both directions, a 3-node hub cluster, and a separate certificate and hub account for every site.

Architecture

Edge apps talk only to the NATS server on their own site LAN. The leaf node at each site dials out to the hub, so the site needs no inbound port and works behind NAT. Each side runs its own JetStream domain (cloud, site1, …), so the cloud can reach a site's streams as $JS.site1.API, and a site reaches its own command consumer in the cloud through $JS.hub.API, both over the same leaf connection. The hub is a 3-node cluster with R3 streams. Sites whose egress allows only HTTPS use the same leaf over wss:// on 443, through an HTTP CONNECT proxy if needed.

Where each message waits during an outage

TrafficWaits onMechanism
Telemetry, health, command results (site → cloud)Site disk: SITE1_UPLINKThe edge app's JetStream publish is acked by the local server, so it succeeds with the WAN down. FLEET_UPLINK sources each site stream and resumes from its last sequence when the link returns. Order is kept, and Nats-Msg-Id deduplicates.
Commands (cloud → site)Cloud disk: FLEET_COMMANDS (R3)The site pulls its own durable consumer siteN-commands through the leaf. Explicit ack; a work-queue stream deletes on ack.
Stale commandsDeleted in the cloudPer-message Nats-TTL (stream has allow_msg_ttl), so a stale command is never shipped. Keep the expiresAt check at the edge as well.
Latest health per robotFLEET_UPLINKA consumer with deliver_policy: last_per_subject on sites.*.health.>

Sizing: SITE1_UPLINK uses discard: new. When the site disk fills during a very long outage, publishes are refused (the app sees an error) rather than old unsent data being silently dropped. Size max_bytes from uplink rate × the longest outage you must survive.

Per-leaf security

Identity: one client certificate per site

The hub's leaf listener uses verify_and_map: true. Each site presents its own certificate signed by the fleet CA, and the certificate subject CN=leaf-siteN,O=fleet is the hub user. There is no shared secret and no password in a URL. Revoking one site touches no other site. A valid CA-signed certificate with an unknown subject is rejected.

Isolation: one hub account per site

Each site's leaf binds to its own hub account (SITE1, SITE2, …); the cloud lives in FLEET. An account sees only what it imports, so isolation is the account boundary, not a list of subject permissions. gen-hub-accounts.sh generates exactly this per site:

DirectionWhat crossesWhy
SITE1 → FLEETservice $JS.site1.API.>
service $JS.FC.SITE1_UPLINK.>
stream fleet.deliver.site1.>		the hub sources SITE1_UPLINK, with its flow control and data
FLEET → SITE1service CONSUMER.MSG.NEXT / INFO on FLEET_COMMANDS.site1-commands (as $JS.hub.API.*)
service $JS.ACK.FLEET_COMMANDS.site1-commands.>		the site pulls and acks its own commands

Nothing else crosses. A site cannot reach another site's consumer, cannot publish commands, and never sees another site's reply subjects. A site1 user with full rights, subscribed to > while site2 worked, saw 0 site2 messages.

Cluster routes

Sites and hubs share the fleet CA, so routes use verify_cert_and_check_known_urls: the peer needs a DNS SAN matching a configured route host, which site certs don't have. A site cert trying to join as a route was rejected on every attempt.

The site LAN has its own limits: edge-app may publish only sites.site1.> (never command requests) and use only its own consumer. site-ops exists for provisioning only.

leafnodes {
  listen: 0.0.0.0:7422

  # to their reconnect list. Left unset, that is the pod/VM's private IP, and
  # leaves will reconnect around your load balancer. Set it to the public name.
  # (no_advertise does NOT cover this: in v2.12.1 it only affects gossip to

    cert_file: "./certs/cloud.crt"
    key_file:  "./certs/cloud.key"
    ca_file:   "./certs/ca.crt"

    # the fleet CA. The cert subject IS the username. No shared secret, no
    # password in a URL, and revoking one site never touches another.
    verify_and_map: true
    timeout: 5
  }
}

# For sites whose egress allows only HTTPS, often through a corporate proxy.
# A site leaf can dial wss://cloud-hub:443, optionally via HTTP CONNECT, and

    ca_file:   "./certs/ca.crt"

  }
}

gen-hub-accounts.sh
#!/bin/bash
# Generate the hub's accounts file: one account per site.
#   usage: ./gen-hub-accounts.sh site1 site2 ... > config/hub-accounts.conf
#
# Why per-site accounts: a site's leaf binds to ITS OWN hub account, and an
# account only sees what it explicitly imports. Isolation is the account
# boundary rather than subject permissions on a shared account, so the reply
# subjects JetStream uses ($JSC.R.*, $JS.FC.*, _INBOX.*) are never visible
# to another site.
#
# What crosses each boundary (nothing else does):
#   SITEn -> FLEET  service $JS.siteN.API.>         hub sources SITEn_UPLINK
#                   service $JS.FC.SITEn_UPLINK.>   flow-control replies for it
#                   stream  fleet.deliver.siteN.>   the sourced messages
#   FLEET -> SITEn  service CONSUMER.MSG.NEXT / INFO for FLEET_COMMANDS.siteN-commands,
#                   imported as $JS.hub.API.* (NOT $JS.cloud.API.*: the hub
#                   intercepts its own domain prefix in every account and
#                   answers "JetStream not enabled for account" first)
#                   service $JS.ACK.FLEET_COMMANDS.siteN-commands.>
set -euo pipefail
[ $# -ge 1 ] || { echo "usage: $0 site1 [site2 ...]" >&2; exit 1; }
for s in "$@"; do [[ $s =~ ^[a-z0-9]+$ ]] || { echo "bad site id: $s" >&2; exit 1; }; done
up() { tr '[:lower:]' '[:upper:]' <<<"$1"; }

echo "# GENERATED by gen-hub-accounts.sh $* -- do not edit by hand"
echo "accounts {"
echo "  FLEET {"
echo "    jetstream: enabled"
echo "    users: [ { user: cloud-app, password: \$CLOUD_APP_PASS } ]"
echo "    exports: ["
for s in "$@"; do S=$(up "$s"); cat <<E
      { service: "\$JS.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.$s-commands", accounts: [$S], response_type: stream }
      { service: "\$JS.API.CONSUMER.INFO.FLEET_COMMANDS.$s-commands", accounts: [$S] }
      { service: "\$JS.ACK.FLEET_COMMANDS.$s-commands.>", accounts: [$S] }
E
done
echo "    ]"
echo "    imports: ["
for s in "$@"; do S=$(up "$s"); cat <<E
      { service: { account: $S, subject: "\$JS.$s.API.>" } }
      { service: { account: $S, subject: "\$JS.FC.${S}_UPLINK.>" } }
      { stream:  { account: $S, subject: "fleet.deliver.$s.>" } }
E
done
echo "    ]"
echo "  }"
for s in "$@"; do S=$(up "$s"); cat <<E

  # ---- $s: its leaf binds here via its client cert ----
  $S {
    users: [ { user: "CN=leaf-$s,O=fleet" } ]
    exports: [
      { service: "\$JS.$s.API.>", accounts: [FLEET] }
      { service: "\$JS.FC.${S}_UPLINK.>", accounts: [FLEET] }
      { stream:  "fleet.deliver.$s.>", accounts: [FLEET] }
    ]
    imports: [
      { service: { account: FLEET, subject: "\$JS.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.$s-commands" }, to: "\$JS.hub.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.$s-commands" }
      { service: { account: FLEET, subject: "\$JS.API.CONSUMER.INFO.FLEET_COMMANDS.$s-commands" }, to: "\$JS.hub.API.CONSUMER.INFO.FLEET_COMMANDS.$s-commands" }
      { service: { account: FLEET, subject: "\$JS.ACK.FLEET_COMMANDS.$s-commands.>" } }
    ]
  }
E
done
echo
echo "  SYS { users: [ { user: sys, password: \$SYS_PASS } ] }"
echo "}"
echo "system_account: SYS"
config/site1-leaf.conf
# =============================================================================
# SITE LEAF  --  site1
#
# Edge apps talk ONLY to this server, on the site LAN.
#  - Uplink (telemetry, health, command results): published into the local
#    stream SITE1_UPLINK. The publish ack comes from THIS server's disk, so it
#    succeeds even when the WAN is down. The cloud copies the stream when the
#    link is back.
#  - Downlink (commands): the edge app pulls its durable consumer on the CLOUD
#    stream through this leaf, via the API prefix $JS.hub.API (the hub maps
#    it, in this site's own hub account, onto FLEET's JetStream API -- see
#    gen-hub-accounts.sh). While the link is down, commands wait in the
#    cloud. Nats-TTL removes them once they are stale.
# =============================================================================
server_name: site1-leaf

# Detect a black-holed WAN (socket open, nothing flowing) in about a minute.
# Defaults are 2m x 2 outstanding (server/const.go), i.e. minutes of a dead
# link that still looks up. Measured with 20s/2: link dropped after 61s.
ping_interval: "20s"
ping_max: 2
listen: 0.0.0.0:4222             # site LAN only

jetstream {
  domain: site1                  # the cloud reaches this as $JS.site1.API
  store_dir: "./data/site1"
  # Size = uplink rate x worst outage you must survive, plus headroom.
  max_file_store: 20GB
  # Every write reaches the OS immediately, so a nats-server crash loses
  # nothing (measured: kill -9 mid-outage, 0 lost). fsync, though, runs only
  # every 2m by default (server/filestore.go defaultSyncInterval), so a POWER
  # cut can lose up to 2m of already-acked uplink. Sites lose power; this
  # closes that window. Measure the cost on the real site disk.
  sync_interval: always
}

accounts {
  FLEET {
    jetstream: enabled
    users: [
      { user: edge-app, password: $EDGE_APP_PASS, permissions: {
          publish:   { allow: [ "sites.site1.>", "$JS.API.STREAM.INFO.SITE1_UPLINK",
                                "$JS.hub.API.CONSUMER.MSG.NEXT.FLEET_COMMANDS.site1-commands",
                                "$JS.hub.API.CONSUMER.INFO.FLEET_COMMANDS.site1-commands",
                                "$JS.ACK.FLEET_COMMANDS.site1-commands.>" ],
                       deny:  [ "sites.site1.command.*.req" ] }
          subscribe: { allow: [ "_INBOX.>" ] }
      }}
      # provisioning only (creates SITE1_UPLINK); not used by apps
      { user: site-ops, password: $SITE_OPS_PASS }
    ]
  }
  SYS { users: [ { user: sys, password: $SYS_PASS } ] }
}
system_account: SYS

leafnodes {
  # Dial OUT. Works behind NAT. The site needs no inbound port.
  remotes: [
    {
      urls: [ "tls://cloud-hub:7422" ]

gen-certs.sh
#!/bin/bash
# Fleet CA, hub server cert, and ONE client cert per site (per-leaf identity).
# usage: ./gen-certs.sh HUB_NAMES site1 site2 ...
#   HUB_NAMES: comma-separated DNS names for the hub cert, e.g.
#   cloud-hub.example.com,cloud-hub-1,cloud-hub-2,cloud-hub-3
#   (the public/LB name that sites dial, plus every route host)
set -euo pipefail
HUB=$1; shift; mkdir -p certs; cd certs
[ -f ca.key ] || openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 3650 -subj "/CN=fleet-ca"
openssl req -newkey rsa:2048 -nodes -keyout cloud.key -out cloud.csr -subj "/CN=${HUB%%,*}"
SAN=$(tr ',' '\n' <<<"$HUB" | sed 's/^/DNS:/' | paste -sd, -)
# clientAuth too: hub nodes are TLS clients of each other on routes
printf "subjectAltName=%s\nextendedKeyUsage=serverAuth,clientAuth" "$SAN" > s.ext
openssl x509 -req -in cloud.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out cloud.crt -days 825 -extfile s.ext
for s in "$@"; do
  openssl req -newkey rsa:2048 -nodes -keyout leaf-$s.key -out leaf-$s.csr -subj "/CN=leaf-$s/O=fleet"
  printf "extendedKeyUsage=clientAuth" > c.ext
  openssl x509 -req -in leaf-$s.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out leaf-$s.crt -days 825 -extfile c.ext
  echo "hub user for $s: \"CN=leaf-$s,O=fleet\"   (form verified against nats-server 2.12.1)"
done
rm -f *.csr *.ext

What the test caught

1. Sourcing over a locked-down leaf. The first permissions draft blocked FLEET_UPLINK: the cloud received 0 messages and logged no error. The source consumer delivers on $JS.S.<rand> and gets its create reply on $JSC.R.<rand> (server/stream.go syncSubject("$JS.S"), server/jetstream_cluster.go infoReplySubject()). Setting external.deliver to a per-site prefix (fleet.deliver.siteN) moves the data onto a subject that can be scoped per leaf.

2. Leaves reconnecting around the load balancer. After the simulated WAN cut, site1 reconnected straight to the hub's private IP. A connecting leaf always receives the hub's own leaf URL (server/leafnode.go: s.leafURLsMap[s.leafNodeInfo.IP]++), and no_advertise only affects gossip to cluster routes (server/route.go). The fix is leafnodes.advertise set to the public name.

3. Domain prefix intercepted. With per-site accounts, the site's command pulls first failed with "JetStream not enabled for account": the hub answers its own domain prefix $JS.cloud.API.* in every account, before an import applies. Sites therefore use $JS.hub.API, which only the import maps.

Behaviours to plan for

  • Catch-up can start late. A source that kept failing waits out its retry backoff, 5s × fails×2 capped at 2 m (server/stream.go). Measured 37–58 s between reconnect and the copy starting. Nothing is lost; commands are pulled, so they are unaffected.
  • Ephemeral consumers after a node loss. For about 3 minutes after a hub node died, ~1 in 3 new R1 ephemeral consumers timed out; nats.go's OrderedConsumer then blocked past its own max-wait. Durable R3 consumers were unaffected. Cloud apps should use durable consumers, or create ephemerals with a short timeout and retry. Not root-caused.
  • Config order. In a leaf remote, proxy { } must come after tls { }, or nats-server 2.12.1 rejects the config.
  • Application side. Delivery is at-least-once: dedupe on commandId, set Nats-Msg-Id on uplink publishes, keep the edge expiresAt check and a per-robot sequence guard, and handle publish errors when the site stream is full.
